4 · Rent GPUPick provider + GPU + count from the decision map. Attach a volume.
5 · ConnectSSH key → VS Code Remote-SSH and/or WinSCP. Start tmux.
6 · InstallCheck driver, create venv, install the right PyTorch wheel, run 00_env_check.py.
7 · Transfer codegit clone (best) or drag the folder with WinSCP.
8 · Download weightshf download to the volume (not the container disk).
9 · BaselineFP16 + naive RTN perplexity. This is the number to beat.

1. Brutal truths before you spend a rupee

  1. AWQ is weight-only 4-bit. It shrinks weights about 3.5–4× and memory at inference roughly 3×. It does not make a from-scratch PyTorch implementation fast. Speed comes from fused kernels (vLLM / SGLang AWQ-Marlin). That's why export to the standard AWQ format (Section 13) matters.
  2. Small models get hurt more. A 1B model typically loses 5–10% perplexity at 4-bit. A 70B model typically loses 1–3%. Code, math and long-context tasks degrade more than perplexity suggests, so always test on your task.
  3. The FP16 baseline is often the most expensive part. Quantizing 70B needs one 80 GB GPU (block-by-block). Evaluating 70B in FP16 needs about 170 GB of VRAM (2–3 GPUs). For a 1T model, an FP16 baseline isn't practical. You compare against the published numbers instead, and the guide says so out loud.
  4. "Trillion-parameter" is a logistics problem before it's a GPU problem. Kimi-K2-class means about 1 TB to download, 2–4 TB of disk, many hours of quantization and an 8-GPU node just to serve the result. Budget hundreds of dollars, not $3.
  5. An AI assistant's hardware estimate is a draft, not a decision. LLMs mis-read configs and hallucinate parameter counts. Option A is fast. Option B and 01_inspect_model.py are the truth.
  6. Tuning on the test set is cheating. All tuning in this playbook uses a held-out calibration-style split. WikiText-2 test and lm-eval are run once, at the end.
  7. Spot / community GPUs get reclaimed. The pipeline writes a checkpoint after every block and resumes automatically. Use tmux. Keep your work on a persistent volume.
  8. Idle GPUs burn money. The most common beginner cost isn't compute. It's forgetting to delete a pod or a volume.

2. Audit of the original Week-37 PDF

I read all 40 pages. The math (Sections 1–2 of the original) is right and the 7-day structure is good. These are the issues that would bite you on a real run, and what the new code does about each:

#Problem in the originalConsequence → fix in this project
1Loads the whole FP16 model onto one GPU for collection, search and eval.Caps out around 30B on an 80 GB card, so it can't do 70B, 405B or 1T. Fix: block-by-block streaming. Only one decoder block plus its calibration activations sit on the GPU. Weights are read shard by shard from safetensors.
2Calibration loader uses padding="max_length".Crashes on Llama tokenizers (they have no pad token), and where it doesn't crash it feeds pad tokens into the statistics. Fix: concatenate texts and cut exact seq_len windows, with no padding.
3The AWQ VRAM figure is measured after loading FP16 to the GPU and swapping layers, without resetting peak stats.The reported "AWQ VRAM" is really the FP16 peak, so the "3× drop" claim can't be measured this way. Fix: build the quantized model on the meta device, load packed weights only, reset peak stats, then measure.
4Scales are searched per single Linear, and 1/s is applied at runtime in every layer.Correct, but slow, and it can't be exported to the standard AWQ format (vLLM expects 1/s folded into the previous norm/linear). Fix: Linears that share the same input tensor (q/k/v, gate/up) are detected automatically and get one scale per group. That scale is folded into the producer for known families (Llama, Mistral, Qwen2/3, Gemma*, Mixtral attention). Unknown families keep a runtime inv_s (always correct, native format only).
5No weight-clipping search. Symmetric only. Normalises s by its mean.Leaves accuracy on the table compared with the official AWQ. Fix: add the AWQ clip search, an asymmetric (zero-point) mode (the default, and the standard format) and the official s/√(max·min) normalisation.
6Excludes the output head by the name "lm_head".GPT-NeoX calls it embed_out and others call it output, so they would get quantized by accident. Fix: only quantize Linears inside the repeated decoder blocks. Routers and tiny layers are skipped automatically.
7The "expected" numbers (e.g. AWQ PPL 9.97, 0.74 GB) are illustrative.Putting them in a blog or README as results would be false. Fix: the repo reports only measured JSON, with the hardware, commit hash and timestamp.
8huggingface-cli loginDeprecated in current huggingface_hub. Fix: hf auth login, hf download, hf upload.
9No resume and no checkpointing.A reclaimed spot pod at hour 5 of a 70B run means starting over. Fix: per-block checkpoints and --resume.
10No MoE, FP8, custom-code or own-model support.Fix: Section 0 table, plus the plug-in hook in 3.4.
KEPT The derivation (y = (x/s)·(W·diag(s))ᵀ, s = mean|x|^α, α grid search), the pack/unpack roundtrip test, the forward-verify gate and the day-by-day pass/fail discipline.

4. Step 2: Size the hardware

You need three answers: which GPU, how many, and for how long, and you need them separately for the three phases. They have very different needs:

PhaseWhat sits in VRAMDriven by
A. QuantizeOne decoder block + calibration activations for that blockLargest block size, n_samples × seq_len, MLP width
B. FP16 baseline evalThe whole model in 16-bit + eval activationsTotal parameters × 2 bytes
C. Evaluate / serve AWQThe whole model in 4-bit + KV cacheTotal parameters × ~0.52 bytes + context length

4.2 Option B: Manual formula (pen and paper)

P      = total parameters (billions)            ← model card / 01_inspect_model.py
P_emb  = vocab x hidden (x2 if lm_head is NOT tied) / 1e9
P_lin  = P - P_emb                               ← the part AWQ quantizes
L, h, I, top_k, I_moe                            ← config.json

FP16 size (GB)          = 2 x P
AWQ size  (GB)          = 0.52 x P_lin + 2 x P_emb      (4 bits + scale/zero per 128 weights ≈ 4.16 bits)
Block (GB)              = 2 x P_lin / L                  (for MoE: count ALL experts in one layer)
Calib act (GB)          = n_samples x seq_len x max(I, top_k x I_moe) x 2 / 1e9

VRAM quantize (GB)      = 2 x Block + 6 x Calib act + 2
VRAM FP16 eval (GB)     = 1.2 x FP16 size
KV cache (GB)           = 2 x L x kv_heads x head_dim x context x batch x 2 / 1e9
VRAM serve AWQ (GB)     = 1.15 x (AWQ size + KV cache)

# GPUs for a phase      = ceil( VRAM_phase / (0.9 x VRAM of one GPU) )
Disk (GB)               = download size + AWQ size + 20
CPU RAM (GB)            ≥ max(16, 3 x Block + 2 x Calib act + 8)     (streaming loader)
# Phase A uses ONE GPU (a block is never split across cards). Phase C (vLLM) uses 1, 2, 4 or 8 GPUs.
Hours (estimate)        ≈ P x 3 min / 60  (A100-class; x1.5 RTX 4090)  + download + 0.5
Cost                    = Σ phases ( #GPUs x $/GPU-hr x hours ) x 1.25   (setup + idle margin)
ESTIMATE The "3 min per billion parameters" speed is my estimate for this pure-PyTorch implementation with clip search on. The first real GPU run calibrates it, and v1.0 of this PDF will carry the measured value.

4.3 Worked example: Llama-3.1-8B

P = 8.03   P_emb = 128256 x 4096 x 2 / 1e9 = 1.05   P_lin = 6.98   L = 32   I = 14336
FP16 size        = 16.1 GB
AWQ size         = 0.52 x 6.98 + 2 x 1.05 = 3.63 + 2.10 = 5.7 GB      (2.8x smaller on disk)
Block            = 2 x 6.98 / 32 = 0.44 GB
Calib act        = 128 x 512 x 14336 x 2 / 1e9 = 1.88 GB
VRAM quantize    = 0.88 + 11.3 + 2 = ~14 GB     → 1x RTX 4090 24 GB
VRAM FP16 eval   = 1.2 x 16.1 = 19.3 GB         → 1x RTX 4090 (tight) or 1x L40S 48 GB (safe)
KV @ 8k          = 2 x 32 x 8 x 128 x 8192 x 2 / 1e9 = 1.07 GB
VRAM serve AWQ   = 1.15 x (5.7 + 1.07) = 7.8 GB → fits a 12 GB consumer card
Disk             = 16.1 + 5.7 + 20 = ~42 GB  (rent a 60–80 GB volume for headroom)
Time / cost      = ~2–3 h on 1x RTX 4090 @ $0.34–0.89/h  →  ≈ $1–3

6.2 Which provider, honestly

  • Default: RunPod community cloud. Cheap, per-second billing, a PyTorch template with drivers ready, persistent volumes, and an easy SSH + SFTP setup. Use secure cloud for long 70B+ runs where getting interrupted costs more than the price difference.
  • Lowest price, and you'll babysit it: Vast.ai. Check the host's disk speed and network before you start a large download.
  • A real VM with root and stable IPs: Hyperstack or Lambda.
  • Paying in INR / GST invoice: E2E Networks or Jarvislabs.
  • 400B–1T: you need a provider with H200/B200 nodes and multi-TB volumes: RunPod (secure), Lambda or Hyperstack. Ask about volume size limits before renting.

7. Step 5: Connect

7.1 Create an SSH key (one time, on your laptop)

# Windows PowerShell (also works on macOS/Linux terminal)

7.4 WinSCP (drag-and-drop files, Windows)

  1. Install WinSCP from winscp.net (the official site only).
  2. New Session: File protocol SFTP · Host name <PUBLIC_IP> · Port <PORT> · User name root (or ubuntu).
  3. Advanced… → SSH → Authentication → Private key file → pick id_ed25519. WinSCP offers to convert it to .ppk. Click OK and save it.

9.1 How the algorithm runs (plain words)

  1. Embed the calibration text. 128 windows × 512 tokens go through the embedding layer. The result is the input to block 0.
  2. For each block i (only this block is on the GPU):
    1. Load block i's weights from disk → GPU.
    2. Run the block once with hooks to record the input of every Linear. Linears that receive the same tensor (q/k/v; gate/up; each expert's gate/up) form a group.
    3. For each group: per-channel importance m = mean|x|. Try 20 values of α ∈ [0,1]: s = m^α (normalised), fake-quantize W·diag(s), compute the group output with x/s, measure the error vs FP16. Keep the best s.
    4. Clip search: for each Linear, try shrinking the max-abs value per group (100%→50%) and keep what minimises output error. This tames outlier weights.
    5. Fold 1/s into the previous norm or Linear when it's known. Otherwise store inv_s in the layer. Then pack INT4 + scales (+ zeros).
    6. Run the quantized block on the calibration data and log its error vs. the FP block (block_rel_mse). The input to block i+1 is the FP block's output (official AWQ behaviour, search.propagate: fp), or the quantized output (propagate: quantized, GPTQ-style, a tuning knob). Save a checkpoint, free the GPU, move on.
  3. Write model.safetensors shards + quant_config.json + a copy of the tokenizer and config.

12. Step 10: Hyperparameter tuning

There's no training in AWQ. The "hyperparameters" are the quantization and calibration knobs. Tuning shrinks the gap to FP16 and can never beat FP16. Each trial costs one full quantize + short eval, so tune in stages. Don't brute-force everything at once.

KnobValues triedTypical effectCost
calib.datasetpileval, c4, your domain dataThe biggest win when your use case is narrow (code, legal, Hindi…). Calibrate on what you'll serve.none
quant.group_size128 → 64 → 32Smaller groups are more accurate. 64 usually recovers a good part of the gap.+3% / +9% size
quant.zero_pointtrue / falseAsymmetric is usually better. Symmetric is simpler.tiny
calib.n_samples × seq_len128×512 → 256×512 → 128×2048Small gains. Helps long-context models.more VRAM/time
search.n_grid20 → 40Marginal.2× search time
search.clip, max_shrinkon/off, 0.5 → 0.3Clip on is almost always better.+30% time
quant.skip_moduleskeep the worst k Linears in 16-bit (from search_log.jsonl), often first/last block's down_projTargeted fix for a few sensitive layers.+size per layer
search.propagatefp / quantizedquantized = later blocks see (and compensate for) earlier rounding errors.none
quant.fold_scalesauto / nevernever = also scale groups that cannot fold (e.g. GQA o_proj), so a bit more accurate. But native format only: no vLLM export.tiny runtime cost

12.1 Protocol (strict)

  1. Tuning metric = PPL on a held-out slice (C4 validation windows not used anywhere else). Never WikiText-2 test or lm-eval.
  2. Stage 1: calibration dataset → Stage 2: group size → Stage 3: samples/length → Stage 4: skip-layers. Carry the winner forward each time.
  3. Stop when the gate in 11.2 is met, or after 3 trials in a row that improve less than 0.5%.
  4. Run the final eval (11.1) once on the winner.
REAL RUN Section 19.7–19.8 shows this protocol on Qwen2.5-0.5B: group 64 was accepted (validation PPL −4.7%), fold_scales=never (−0.1%) and quantized propagation were rejected, and the final test-set gap went from +16.0% to +10.7%.
